# Prevent cross-entry fact conflation in the prompt, not with a detector

Status: accepted

A generated resume summary read "led CRM data-migration validation for a $10,000-budget organization" — a false composite. "CRM data-migration validation" is real, from the Development Specialist Intern (DDAR) entry; "$5,000–$10,000 annual budget" is real, from a completely different entry (Vice President External Affairs, Penn State Malaysian Students Club). The model fused two individually-true facts from unrelated entries into one sentence that misattributes the budget to the wrong organization.

`check-profile-fidelity.ts` didn't catch this because it only verifies each number/fact exists *somewhere* in the profile text (a substring check across the whole corpus), not that a given sentence doesn't stitch two entries' facts together. A reliable automated detector for this would be a fuzzy attribution problem (which entry does this clause "belong" to?), not an exact-match one, and would only catch the bug after a paid generation call anyway.

Fixed at the root instead: added an explicit "NO CROSS-ENTRY FACT MIXING" rule to `CORE_RULES` in `lib/claude.ts`, with the exact DDAR/student-club failure case spelled out as a worked example. This is the cheapest available fix, since `CORE_RULES` is the cached prompt block shared by both resume and cover-letter calls (see `0001-shared-core-prompt-for-cross-task-caching.md`) — the rule costs nothing extra per call after the first cache write.

**Considered and rejected:**
- Banning specific numbers from the summary field entirely — would remove the ambiguity structurally, but felt like cutting a feature to work around a prompt gap rather than fixing the gap.
- A fully general automated post-hoc detector in `check-profile-fidelity.ts` — rejected as originally scoped (fuzzy attribution, not substring matching) and only catches the failure after money's already been spent generating it.

**Update (see verification session that added prompt rules 2e/2f to `lib/claude.ts` for a related class of bug — qualifiers/hedges getting dropped during summarization):** that session established, by actually generating real resumes and reading the output, that a written prompt rule is necessary but not sufficient on its own — it can still be silently violated in ways nobody notices until a human reads the actual generated text. Rather than leave this as an open, unstated risk, the plan is now explicit and split in two:

1. **Automated, but scoped narrowly:** `check-profile-fidelity.ts` now includes a *targeted* (not fully general) cross-entry check: every generated bullet's numeric claims must trace back to that bullet's OWN experience/project entry (not just exist somewhere in the profile), and no single summary sentence may fuse numbers uniquely traceable to two different entries. This is cheap to compute (reuses the existing per-entry number extraction) and directly catches the exact failure pattern in this ADR's original bug report. It does NOT catch non-numeric fact mixing (e.g. fusing a qualitative claim from one entry with another's context) — that remains the harder, rejected fuzzy-attribution problem.
2. **Manual, but designed rather than assumed:** the preview page (`app/preview/page.tsx`) now shows a fixed pre-send checklist next to the "Save as PDF" button, naming the specific things to check (cross-entry mixing, dropped qualifiers, verifiable numbers/dates/titles) — turning "eyeball it" from an unstated assumption into an actual, repeatable step in the product, for the failure modes that can't be cheaply automated.

**Consequence:** cross-entry numeric mixing in bullets and summary sentences is now caught automatically before a real send (if `npm run check:fidelity` is run) or at minimum surfaced as an explicit manual check in the UI. Non-numeric fact mixing and semantic qualifier-dropping remain manual-by-design, backed by the checklist rather than by memory alone. If either recurs, prefer sharpening the relevant prompt rule and, where the failure is numeric/structural, extending the fidelity check — over building the fully general fuzzy-attribution detector, which is still not worth the cost for a single-user tool.
